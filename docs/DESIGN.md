# chronofit 設計 — 「実際にどれだけかかったか」から予定を組む

## 0. なぜ作り直すのか（過去3回の失敗の実測）

計測は3回試して3回とも死んでいる。原因は「続かない性格」ではなく、**どれも人間の手動操作を
計測ループの中に置いた**こと。実測:

| 試み | 期間 | 実績 | 死因 |
|---|---|---|---|
| Clockify 手動タイマー | 2025-12-17〜2026-02-04 | 188 entries / 201h / 記録日 38/50日 (76%) | 開始・停止の手動操作 |
| Notion タスクDB | 同期間 | 168 tasks | 記録されるのが **リードタイム**（例: 可燃ごみ袋 168.6h）で所要時間ではない |
| 自前の日次 timelog | 2026-06-27〜29 | **2日分** | 1日ごとに全区間へ本人申告の散文を書く＝毎日インタビュー |

Clockify のデータには**もう一つの毒**がある。4時間以上のエントリが10件あり、それだけで
**全201時間の34%（67.4h）**を占める。10.2h「ブックマーク整理」・9.1h「物理」・9.0h「物理期末」
——止め忘れである。つまり手動タイマーは *続かない* だけでなく、続いている間のデータも
**だらけ時間を中に含んだまま**記録する。今の見積もりのバッファに slack が紛れ込んでいる問題は、
測り方そのものに由来している。

一方、**人間が何もしなくても今日まで生き残っている記録**がある: ブラウザ履歴・git コミット・
音声メモの録音。これらは誰も操作しないので死にようがない。

> **設計原則: 人間を計測ループから外す。人間の仕事は「後追いの、まとめて、1タップの確認」だけ。**

## 1. 4層モデル

### L0 端末イベント（完全自動・操作ゼロ）— 新規

15秒ごとに前景ウィンドウと入力アイドル秒をサンプリングし、変化点でスパンに畳んで JSONL に落とす。
Windows API を ctypes で直に叩くので**依存パッケージゼロ**。

取れるもの:

- **プロセス名 + ウィンドウタイトル** — ここが決定的。タイトルは作業の *対象* を持っている:
  `応用数学A_2024_期末.pdf - SumatraPDF` / `t-distribution.tex` / `PROJ-14 - Jira`。
  ブラウザ履歴だけでは PDF もエディタも見えない。**(科目 × 種別 × 何本目) のキーはここから取る。**
- **入力アイドル秒**（`GetLastInputInfo`）— 「PCが固定画面のまま別のことをしていた分まで
  作業時間に計上されてしまう」という積年の誤差はこれで消える。前景が PDF でもアイドル3分超なら
  在席として数えない。
- **ロック/スリープ** — 在席区間の硬い境界。

### L1 既存の自動痕跡（回収するだけ）

- **ブラウザ履歴** — ただし**毎日スナップショットが要る**。実測で Vivaldi の履歴は
  **2026-07-25 以降の16日分しか残っていない**（7184 visits）。Chromium は勝手に刈る。
  いま何もしなければ蒸発し続ける。
- **git コミット**（`~/dev/*` の author date）— 何をいつ作ったかの動かぬ証拠。
- **Claude Code セッションログ** — タイムスタンプ付き。扱っていた科目が分かる。
- **音声メモの録音** — 時刻付き。内容がそのまま「何をしていたか」。

### L2 オフPC（本題）

**音声・カメラの常時録画は採らない。** 理由は privacy でもコストでもなく設計上の必然:
それは「起動を忘れうる仕組み」をもう一つ増やすだけで、しかも誰もラベルを付けない大量のデータを
生む。過去3回と同じ死に方をする。

代わりに: **L0 が離席ブロックの「長さ」を既に秒単位で持っている。** 測る必要があるのは長さではなく
**ラベルだけ**である。

- 離席の開始時でも終了時でもなく、**1日の終わり（または次に座ったとき）にまとめて**、
  15分以上のギャップを一覧で出し、各行を5択のボタンで潰す。1日あたり6〜10タップ・30秒。
  1日分なら記憶は十分もつ。
- 2週間も溜まれば**既定値を履歴の最頻値から埋める**（平日 07:30-08:10 は身支度+移動、
  12:00-12:40 は昼食）。ユーザーは例外だけ直す。タップは1日1〜2回に落ちる。

**重要なのは、聞かれるのが「ギャップ」についてだけだという点。**「今から過去問を始めます」と
宣言する必要は一度もない。作業側のラベルは L0 から導出する。

#### 紙で解いた90分の中身をどこから取るか

ラベルが5択で済むのは移動や食事だけで、**紙の過去問や紙の本を所要時間DBへ入れるには
科目と対象が要る**。ここを毎回手で書かせると、結局それが「1日1回のインタビュー」になり、
§0 と同じ死に方をする。

答えは、**中身を離席そのものではなく両隣から取る**ことにある。紙で解いているあいだ PC は
無入力のままだが、人は必ずその前後で PC を触っている — 問題 PDF を開く → 90分の離席 →
同じ科目の解答 PDF を開く、という並びになる。したがって:

- **長さ** は L0 が既に秒で持っている。
- **中身** は直前・直後の前景タイトルへ利用側の `title_rules` を当てて推定する
  （`model/context.py`）。30分以上離れた前景は、その離席の文脈とみなさない。
- 推定が当たったブロックは **Enter 1打**で確定する。手で科目を打つのは
  「PC を一度も触らずに紙だけで進めた」ブロックだけになる。
- 科目と対象を聞くのは `study: true` を付けた選択肢を選んだときだけ。昼食や移動には聞かない。

推定はあくまで**既定値**であって実測ではない。当たらなかったときに当てずっぽうを既定値へ
昇格させない — 間違った推定を Enter で確定させるほうが、聞かれるより害が大きい。

紙のぶんは `done --offpc` でラベルから拾う（`estimate/offpc.py`）。オフPC時間に net と wall の
区別は置かない。本を読んでいるあいだ手は止まらないので、離席時間がそのまま net である。
「読みながら寝ていた」ぶんは測れないが、それはカメラを付けても解決しない種類の誤差なので、
測らないと決めている。

### L3 所要時間DB（消費側）

タスク1インスタンス = 1行:

```
task_instance
  科目        応用数学B
  種別        過去問 | マセマ | 講義資料読み | レポート | 実装
  対象        2024年度期末
  通し番号    その(科目,種別)で何本目か     ← 学習曲線の軸
  net_hours   在席かつ当該対象が前景だった時間（アイドル控除後）
  wall_hours  着手〜完了の実時間（中断込み）
  slack_hours wall - net の内訳（何が挟まったか）
  sessions    何回に分けたか
```

**`net` と `wall` を両方持つことが、バッファ問題の解**である。

- `net_hours` → 学習曲線 `est_net(科目, 種別, n)`。
- `net/wall` 比 → **日タイプごとの実測定数**（例: 平日夜 0.55 / 休日 0.40）。勘で置かない。
- 予定に必要な暦時間 = `est_net(科目,種別,n) ÷ slack_ratio(日タイプ)`。
  カレンダーが持っているのは暦時間なので、容量はここで初めて突き合わせられる。

これは既存の見積もりモデルを置き換える。従来型の `estimate_sequence = [6, 3.5, 3, 3, 3]`
のような系列は **slack 込みの wall 値**なので、実測と照合しようがない。net と slack 率へ
分解して初めて、どちらがズレたのかが分かる。

過去の手動タイマーのエクスポートは取り込むが、**このDBの初期値には使えない**。
実データを見ると、記録されているのはほとんどが PC 雑務で、`(科目, 種別, 通し番号)` の
構造を持つ行はごく僅かしかない。加えて4時間超の止め忘れが全体の34%を占める。
取り込みの目的は履歴の保全と汚染率の把握であって、学習曲線の初期値ではない。

したがって曲線は **L0 の実測から前向きに育てる**。タスクが1本終わったら
`done --match <タイトルの正規表現>` で、かかった時間を実測から拾ってDBへ入れる。
人間が言うのは「終わった」だけで、何時間かかったかは思い出さない。

#### 過去問以外をどう扱うか（種別の3モード）

学習曲線は強力だが、**繰り返しに意味がある種別にしか当たらない**。全部を曲線で扱おうとすると、
繰り返さないタスクに架空の逓減が付き、習慣に架空の締切が付く。種別を3つに分ける
（`estimate/kinds.py`。どの種別がどれかは科目構成で変わるので、表は利用側の `kind_modes` が持つ）:

| モード | 例 | 何が起きるか | 見積もり方 |
|---|---|---|---|
| `series` | 過去問・マセマ1章・AtCoder 1問 | 繰り返すほど速くなる | 学習曲線 |
| `oneoff` | レポート・環境構築・書籍の購入判断 | 通し番号に意味が無い | 同種の実測の中央値と p80 |
| `habit` | ピアノ・筋トレ | 時間が入力であって出力ではない | 見積もらない。**容量から先に引く** |

3つ目が要になる。毎日2時間のピアノをタスクとして積むと、夏休み1か月で需要が60時間ぶん
膨らんだように見える。実際に起きているのは **1日の使える時間が2時間減ること**だけで、これは
見積もりではなく容量の問題である。需要側に置くと、他を削る判断が「ピアノを削るか」と混ざって
決まらなくなる。`chronofit capacity` は習慣を引いた割り当て可能時間を出す。

`oneoff` を平均でなく**中央値と p80** で出すのは、一点物の分布が右に長い尾を引くため。平均は
数件の長引いた例に引きずられ、中央値だけでは楽観になる。予定には p80 を、見通しには中央値を使う。

モードは**行に焼いて保存する**。後から設定を変えても、既に測った行の解釈が遡って変わらない
ようにするためで、学習曲線は `mode == series` の行だけで当てる（一点物の40時間が過去問の
曲線を壊さない）。

## 2. リポジトリ分割

個人データとロジックを切る。ロジック側は個人情報を一切持たないので公開できる。

| 層 | 置き場 | 公開 | 中身 |
|---|---|---|---|
| ロジック | **`chronofit`**（本リポジトリ） | **public** | 収集デーモン・アダプタ・集計・学習曲線・容量フィット・スキル定義 |
| 個人設定 + 日次ロールアップ | 利用側の private リポジトリ | private | 科目定義 / 進捗 / 日次ロールアップ / 課題管理・カレンダー設定 |
| 生イベント | `%LOCALAPPDATA%\chronofit\raw\` | **git 外** | ウィンドウタイトル込みの生ログ。private リポジトリにも置かない |

生イベントを git に入れない理由: ウィンドウタイトルは「今まで開いた全ウィンドウの題名」であり、
private リポジトリでも置く水準を超えている。GitHub へ出るのは**カテゴリ別の集計値と
タスクインスタンス**だけ。

公開側に個人固有の定数（科目名・容量・分類ルール）を焼き込まないことが、そのまま
「設定で動く汎用ツール」であることを強制する。分類ルールは private 側の YAML から注入する。

## 3. 課題管理 / カレンダーとの役割分担

役割を混ぜない。

- **課題管理（Jira 等）** = **締切とバックログの正**。時間の保管場所にはしない。
  既存の同期設定があるならそのまま使う。
- **カレンダー（専用のもの）** = 時刻付きミクロブロックの出力先。
- **chronofit** = 実測と見積もりの正。上3つはどれも「実際に何時間かかったか」を持っていない。

有料 SaaS を入れない判断はここで決まる。市販のトラッカーは合計時間は出すが、
**(科目 × 種別 × 何本目) で引ける所要時間DB**は出さない。そこが唯一の価値であり、
収集デーモン自体は150行程度で済む。

## 4. スキル

`skills/plan/SKILL.md` をリポジトリで管理し、`~/dotfiles/claude/skills/` から
junction で参照する（`agents.md` の設定ディレクトリ運用と同じ流儀）。

呼び出すと: タスク集合を受け取る → DB を照合 → `est_net ÷ slack_ratio` で暦時間へ →
容量に earliest-fit → `plan.md` を出し、必要なら Jira / カレンダーへ流す。

## 5. 作る順序（これは順序が重要）

**収集だけが「後から取り返せない」。** 見積もりエンジンはデータさえ溜まればいつでも書けるが、
今日収集していない日は永遠に空白のままである。したがって:

1. **L0 収集デーモン + 自動起動** ← 最優先。1日遅れるごとに1日分失う
2. ブラウザ履歴の日次スナップショット（放置すると刈られて消える）
3. 既存エクスポート（Clockify / Notion 等）のバックフィル。過去データの保全も兼ねる
4. ロールアップ（スパン → 在席ブロック → net/wall 分離）
5. ギャップ・ラベリング UI（1日1回・数タップ）
6. 所要時間DB + 学習曲線フィット
7. 容量フィット + スキル化

## 6. 強制力について

計測は「どれだけかかったか」には答えるが、「なぜ着手しなかったか」には答えない。強制力は
別途、外部締切と週次ゴールで作る。計測でそこを埋めようとしない。

ただし計測が一つだけ受動的な強制力を生む: **何もしなくても毎日出てくる数字**。
statusline かダッシュボードに「今日の net 学習時間」を常時出す。催促ではなく、ただのスコアボード。
