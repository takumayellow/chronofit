# schedule-plan — 実測から見積もって予定を組む

## このスキルの立場

見積もりを**勘で書かない**。`chronofit` が測った実績を引いて数字を出す。実績が無い項目は
`仮` と明示して仮値を置き、**次に測る対象として記録する**。仮値を実測のように書かない。

前提となる道具は `chronofit`（public / 依存パッケージなし）。個人の科目定義・容量・
分類ルールは利用側の private リポジトリから注入されている。

## 手順

### 1. タスクを構造化する

渡されたタスクを `(科目, 種別, 対象, 通し番号)` に分解する。種別の既定は
`過去問 / 参考書 / 講義資料読み / レポート / 実装 / 暗記`。

粒度の目安は **1インスタンス = 1〜6時間**。「応用数学Bをやる」は分解が足りない。
「応用数学B 過去問 2024年度期末（3本目）」まで落とす。**通し番号が要**で、これが無いと
1本目の重さと5本目の軽さが混ざって、どちらの予定にも使えない数字になる。

そのうえで、種別を**3モードのどれか**に振り分ける。振り分けを間違えると見積もりが壊れる。

| モード | 当てはまるもの | 扱い |
|---|---|---|
| `series` | 過去問・参考書の章・演習 | 通し番号で学習曲線を当てる（既定） |
| `oneoff` | レポート・環境構築・事務・調査 | 通し番号に意味が無い。中央値と p80 |
| `habit` | ピアノ・毎日の精進 | **見積もらない。容量から引く** |

`habit` を needs 側に積むと「毎日2時間 × 33日 = 66時間のタスク」という無意味な数字が出る。
毎日やるものは需要ではなく容量の目減りとして扱う。振り分けは private 側の `kind_modes` に持つ。

### 2. 実測DBを引く

```bash
python -m chronofit coverage                      # DBに何が溜まっているか（信頼度の確認）
python -m chronofit estimate <科目> <種別> [--index N] [--assumed H]
```

`estimate` は3段で答え、どの段で出したかを必ず返す:

| 根拠 | 意味 | 予定での扱い |
|---|---|---|
| `実測` | その (科目, 種別) の実績から | そのまま使う |
| `流用` | 同じ種別の他科目から | 使うが、外れる前提で余裕を持つ |
| `仮` | 実績も流用元も無い | 使うが、**「次に測るべきもの」に必ず載せる** |

`--index` を省くと実績の次の番号を自動で使う。仮値すら渡さなければ**数字を出さない** —
根拠の無い数字を実測の顔で予定に入れないため。

### 3. 暦時間に直す

```bash
python -m chronofit slack     # 日タイプごとの slack 率（平日 / 休日 / 出社）
```

```
必要な暦時間 = est_net ÷ slack_ratio(日タイプ)
```

**勘でバッファを積まない。** 従来の「これだけあれば終わるだろう」という見積もりは、
バッファの中にだらけた時間を抱き込んでいて、外れたときに「作業が重かった」のか
「時間が溶けた」のかを分離できない。slack 率は在席に対する入力ありの割合の実測値で、
平日夜と休日で体感2倍近く違う。

該当する日タイプの率がまだ無ければ、**暦時間へ換算しない**。換算できないと書く。

### 4. 使える時間へ割り付ける

```bash
python -m chronofit capacity --days N     # 暦 - 習慣 = 割り当て可能。slack 率があれば実作業ぶんまで
```

- 容量は**暦時間**で持つ。カレンダーの既存予定・出社日・固定の拘束を先に引く。
- 締切のあるものから earliest-fit。締切は課題管理（Jira 等）の due date を正とする。
- 1日に詰め込みすぎない。実測の日次上限を超える配置はしない。

### 5. 出力

必ずこの3つを添える:

- **見積もりの根拠** — 各項目が `実測 n件` / `流用` / `仮` のどれかを1行で
- **入りきらなかったもの** — 容量を超えて落とした分を隠さず列挙する
- **次に測るべきもの** — 仮値になった項目

## やってはいけないこと

- 実績が無いのに、あるかのような具体的な数字を出す
- 容量に入らないタスクを黙って落とす（落とすなら明示して、要否の判断をユーザーに返す）
- 時刻単位まで割り付けて満足する。**遂行されない粒度の計画は作っても意味がない**
  — 実測で「カレンダー通りには全く動けない」ことが分かっている。既定は**週単位のゴール**、
  時刻ブロックは本人が明示的に望んだときだけ。

## 週次レビュー（このスキルの相方）

計画は立てた時点では価値が無い。価値は**実測と突き合わせて次の見積もりが良くなる**ことにある。
週に一度、15分:

```bash
python -m chronofit status                  # 収集が動いているか
python -m chronofit rollup --date YYYY-MM-DD
python -m chronofit label                   # 未ラベルの離席ブロックを潰す（数十秒）
python -m chronofit slack                   # slack 率の更新を見る
python -m chronofit history --days 7        # ブラウザ履歴の分類。未分類が重いドメインは規則へ写す
```

終わったタスクは所要時間DBへ入れる。紙でやったものは離席ラベルから拾える:

```bash
python -m chronofit done <科目> <種別> --match <対象>   # PC作業ぶんを実測から
python -m chronofit done <科目> <種別> --offpc          # 紙でやったぶんを離席ラベルから
python -m chronofit done <科目> <種別> --net 5400       # どちらでも取れないときだけ手入力
```

1. 計画とのズレを見る。**ズレたら計画を直す。自分を責める材料にしない**
2. ズレの原因を `est_net` 側と `slack_ratio` 側に分けて読む
3. 見積もりが外れた項目は実測値でDBを更新する
4. 次の週のゴールを3つだけ決める
